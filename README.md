# dsh-sync

Кроссплатформенная синхронизация сессий [DeepSeek Harness](https://github.com/deepseek-ai/dsh)
между устройствами: Windows ↔ macOS ↔ Linux.

Сессии хранятся в зеркале с **нейтральным абсолютным путём**, поэтому разные
пути проектов и разные ОС больше не мешают продолжить разговор с другого
компьютера.

```
устройство A:  C:\work\my-project   ──push──▶  /dsh-sync/projects/myproject
устройство B:  /Users/me/work/proj  ◀──pull──  /dsh-sync/projects/myproject
```

Почему это работает: `path.isAbsolute("/dsh-sync/projects/x")` истинно и на
Windows, и на POSIX, поэтому заголовок сессии остаётся валидным на любой
платформе. Локальный путь подставляется при `pull`, нейтральный — при `push`.

## Установка

Нужен только Node.js ≥ 22.15 (в самом DSH уже есть встроенный рантайм) и,
для git-бэкенда, `git` в PATH. Зависимостей нет.

```bash
git clone https://github.com/<you>/dsh-sync.git
cd dsh-sync
node cli.mjs            # краткая справка
```

На Windows рядом лежит `dsh-sync.cmd` — можно вызывать как обычную команду:

```powershell
.\dsh-sync.cmd status
```

## Два бэкенда

| Бэкенд | Что это | Когда |
|---|---|---|
| `git` | приватный репозиторий (GitHub, GitLab, свой сервер) | нужна история, откат, доступ с других машин |
| `folder` | обычная папка на диске | OneDrive, Яндекс.Диск, iCloud Drive, Syncthing, сетевой шар |

`folder` не требует git вообще: файлы кладутся прямо в синхронизируемый
каталог, а переносом занимается клиент облака.

## Плагин в DSH

Тот же пакет работает и как плагин: карточка в настройках, проверка окружения и
кнопка синхронизации.

```bash
dsh plugin --profile <profile> add dsh-sync
```

Или вручную: добавить `link:`-зависимость и имя бандла в `dsh.profile.bundles`
профиля, выполнить `pnpm install` в каталоге профиля и перезапустить DSH.

Что появляется после перезапуска:

- **карточка «Синхронизация сессий»** в Настройки → Плагины: проверка окружения
  (Node.js, git, папка проекта, доступ к репозиторию), поля «адрес репозитория»,
  «путь к проекту», «идентификатор проекта», флажок вложений и кнопки
  «Сохранить», «Синхронизировать», «Только принять», «Только отправить»;
- **свёрнутая карточка** показывает состояние (`готово` / `не настроено`),
  счётчики `локально/в зеркале` и время последнего запуска;
- **кнопка в шапке сессии** рядом со значком проводника: разовая синхронизация без открытия настроек (крутится во время работы, зелёная — успех, красная — ошибка);
- **инструменты для модели**: `sync_status` и `sync_run`;
- **маршруты** `/api/dsh-sync/state|config|run` для карточки.

Настройки хранятся в том же `~/.dsh/dsh-sync.json`, что использует CLI, поэтому
карточка и командная строка всегда видят одно и то же.

### Где выполняется синхронизация

Карточка и инструменты живут в host-процессе DSH, но сама синхронизация
запускается отдельным процессом на штатном Node (lib/sync-child.mjs): в
сборке, встроенной в приложение, декодер zstd строже проверяет контрольную
сумму кадра, поэтому разбор логов и файловый обход выполняются там, где
поведение совпадает с CLI.

### Подключение нового устройства

После `dsh plugin add dsh-sync` и одного входа в GitHub ничего вводить не нужно:

1. путь и идентификатор проекта берутся из первого workspace DSH;
2. адрес репозитория ищется в аккаунте GitHub по сохранённому в DSH токену
   (имена `dsh-sessions`, `dsh-sync-sessions`, `dsh-sync`);
3. в зеркале лежит `projects.json` — по нему новое устройство понимает, какие
   проекты уже синхронизируются, и сопоставляет их с локальными папками по имени.

Если репозитория нет или токен не сохранён — остаётся ручной ввод адреса в
карточке плагина.

### Автосинхронизация

По умолчанию плагин работает сам, без кнопок:

- **приём** — через 10 секунд после старта DSH, дальше раз в 15 минут;
- **отправка** — при появлении изменений в сессиях, но не чаще раза в 5 минут
  (иначе репозиторий зарастает коммитом на каждое сообщение);
- изменения определяются по отпечатку списка сессий из сервиса DSH, а не по
  обходу каталогов.

Настройки в `~/.dsh/dsh-sync.json`:

```json
"autoSync": {
  "enabled": true,
  "pullOnStart": true,
  "pushOnChange": true,
  "pushMinIntervalMinutes": 5,
  "pullIntervalMinutes": 15
}
```

Если проекты не заданы, плагин подставляет первый workspace из DSH: путь и
идентификатор (из имени папки) заполняются сами.

### Взаимодействие с другими плагинами синхронизации

Перед каждой синхронизацией плагин проверяет, не установлен ли уже другой
плагин для синхронизации сессий (`dsh-session-sync` и подобные):

| Что найдено | Что делает dsh-sync |
|---|---|
| Плагин опубликовал сервис с методами `pull`/`push`/`sync` | синхронизация идёт **через него**, встроенный движок не запускается |
| Плагин установлен в профиле, но интерфейса не публикует | работает встроенный движок, карточка предупреждает о втором плагине |
| Ничего не найдено | работает встроенный движок |

Приоритет внешнего плагина отключается флажком в карточке или полем
`useExternal: false` в конфигурации — тогда всегда используется встроенный
движок.

Два плагина не должны писать в один и тот же стор одновременно: если внешний
плагин активен и настроен, оставьте синхронизацию за ним.

## Быстрый старт

```bash
# 1. конфигурация устройства (создаёт ~/.dsh/dsh-sync.json)
node cli.mjs init --backend git \
  --remote https://github.com/<you>/dsh-sessions.git \
  --attachments

# 2. какой локальный путь соответствует проекту в зеркале
node cli.mjs project add myproject --path "C:\work\my-project"

# 3. отправить / принять
node cli.mjs push
node cli.mjs pull
```

Первый `push` создаёт ветку `main` в пустом репозитории. Аутентификация — через
штатный Git Credential Manager, токен в конфиг не попадает.

Репозиторий зеркала должен быть **приватным**: в сессиях лежит вся переписка,
включая содержимое файлов.

Для облачной папки:

```bash
node cli.mjs init --backend folder --repo "/Users/me/YandexDisk/dsh-sync" --attachments
node cli.mjs project add myproject --path "/Users/me/work/proj"
```

## Проверка на другом устройстве

Инструкция рассчитана на второй компьютер с уже установленным DSH и другим
локальным путём к тому же проекту. В примере — `C:\work\my-project` на первом
устройстве и `/Users/me/work/proj` на втором; подставьте свои.

### 1. На втором устройстве настройте то же зеркало

```bash
git clone https://github.com/<you>/dsh-sync.git
cd dsh-sync
node cli.mjs init --backend git --remote https://github.com/<you>/dsh-sessions.git --attachments
node cli.mjs project add myproject --path "/Users/me/work/proj"
```

`project add` — единственное место, где указывается локальный путь. Идентификатор
(`myproject`) должен совпадать с тем, что был использован на первом устройстве:
именно по нему сессии находят друг друга в зеркале.

### 2. Примите данные

```bash
node cli.mjs pull
```

Ожидаемый вывод:

```
импортировано: 7
обновлено:     0
конфликтов:    0
без изменений: 0, локально новее: 0, открыто: 0
вложений восстановлено: 106

перезапустите DSH, чтобы новые сессии появились в списке
```

Проверьте, что файлы легли в бакет вашего локального пути:

```bash
node cli.mjs status
```

```
myproject  (/Users/me/work/proj)
  локально: 7, в зеркале: 7, только локально: 0, только в зеркале: 0
```

### 3. Перезапустите DSH и проверьте интерфейс

Сессии регистрируются при старте, поэтому перезапуск обязателен. После него в
списке появится workspace с вашим локальным путём и сессиями из зеркала.
Откройте любую — история сообщений должна быть на месте, а новые сообщения
должны работать (папка проекта на втором устройстве должна существовать).

### 4. Проверьте обратный путь

На втором устройстве продолжите любую сессию, затем:

```bash
node cli.mjs push
```

На первом устройстве:

```bash
node cli.mjs pull
```

Ожидаемо: `обновлено: 1` — новые события приехали как fast-forward, без
конфликта, историю переписывать не пришлось.

### 5. Проверьте, что расхождение не теряет данные

Это самый важный тест. Остановите синхронизацию и допишите сообщение в **одну и
ту же** сессию на двух устройствах (например, отправьте по сообщению в каждом).
Затем на первом:

```bash
node cli.mjs push
```

на втором:

```bash
node cli.mjs pull
```

Ожидаемый вывод на втором:

```
конфликтов:    1
  fork: session-<id> → session-<новый-id>
```

Локальная сессия остаётся нетронутой, а версия с первого устройства приезжает
отдельной сессией. Ничего не перезаписывается молча.

### 6. Если что-то пошло не так

- `pull`/`push` ничего не меняют в открытых сессиях: рядом с логом лежит
  `session.lock`, такие сессии пропускаются (`открыто: N`). Закройте DSH и
  повторите.
- перед перезаписью локального лога копия кладётся в `~/.dsh/dsh-sync/backups/`.
- состояние «что это устройство отправляло» — в `~/.dsh/dsh-sync/state.json`;
  его удаление безопасно, следующий `push` просто заново запомнит состав.
- конфигурация — `~/.dsh/dsh-sync.json`, её можно править руками.

## Команды

```
dsh-sync init --backend git|folder --repo <каталог> [--remote <url>] [--branch main] [--attachments]
dsh-sync project add <id> --path <локальный путь> [--title <название>]
dsh-sync project list | remove <id>
dsh-sync status
dsh-sync push [--project <id>] [--no-prune]
dsh-sync pull [--project <id>] [--dry-run]
```

Общий ключ `--home <каталог DSH>` (по умолчанию `$DSH_HOME` или `~/.dsh`).

## Как решаются расхождения

Лог сессии — append-only: заголовок и цепочка zstd-фреймов с событиями, поэтому
сравниваются хвосты после заголовка:

- хвосты совпадают → ничего не делать;
- локальный хвост — префикс удалённого → приехали новые события, применяем
  (старая версия уходит в бэкап);
- удалённый хвост — префикс локального → локально новее, применяем при `push`;
- хвосты разошлись → локальная сессия остаётся, удалённая импортируется
  отдельной сессией с новым id.

Удаление сессии распространяется только на «свои» сессии: устройство помнит,
что отправляло, и не удаляет из зеркала то, чего само не видело.

## Вложения

С `--attachments` синхронизируются объекты `~/.dsh/attachments/v1/{objects,
file-objects,files}`. Они адресуются по sha256, поэтому копируются только
недостающие файлы и никогда не перезаписываются. Кеш `request-images` и
`tmp` в зеркало не попадают.

## Ограничения

- после `pull` нужен перезапуск DSH: сессии подхватываются при старте;
- заголовок сессии (title) хранится в кеше проекций и на другом устройстве
  пересобирается из лога;
- открытые сессии не перезаписываются;
- шифрования содержимого нет — зеркало должно быть приватным.

## Проверка

```bash
node test/sync.test.mjs        # перенос, fast-forward, конфликт, удаление
node test/attachments.test.mjs # вложения по sha256, без кеша и tmp
node test/git.test.mjs         # последовательность git-команд
node test/live-git.mjs         # живой круг A → remote → B → remote → A
```

Тесты не требуют сети: sync и вложения проверяются на бэкенде `folder`, git —
на подменённом исполнителе команд. `live-git.mjs` создаёт временный
bare-репозиторий и требует установленного git.
