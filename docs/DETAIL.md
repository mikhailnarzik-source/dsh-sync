# Синхронизация сессий

Плагин переносит историю диалогов между компьютерами так, чтобы работа не
начиналась заново на каждой машине.

## Как это выглядит в интерфейсе

- **Пункт «Синхронизация сессий»** в левой панели: нажатие сразу запускает
  приём и отправку и показывает результат крупной лампочкой.
- **Карточка плагина** (Настройки → Плагины): состояние, настройки хранилища,
  проверка окружения, диагностика и обновление.
- **Точка перед названием сессии**: зелёная — совпадает с копией, оранжевая —
  есть неотправленные изменения, красная — ещё ни разу не отправлялась.

## Где будут лежать данные

Выбирается в карточке, один раз:

| Хранилище | Что нужно | Когда удобно |
|---|---|---|
| Git-репозиторий | приватный репозиторий, вход в GitHub | есть история версий, работает быстро |
| Папка облака | клиент Яндекс.Диска или OneDrive | без токенов, синхронизирует сам клиент |
| Яндекс.Диск (WebDAV) | логин и пароль приложения | без установки программы |
| Яндекс.Диск (API) | OAuth-токен | если нельзя поставить клиент и нет WebDAV |

Можно указать **резервное хранилище**: сессии уедут в оба места, а при
недоступности основного приём пойдёт из резервного.

## Что происходит само

1. Через 3 секунды после запуска — приём изменений с других устройств.
2. Новые сессии привязываются к рабочему пространству и появляются в списке.
3. Изменения отправляются при каждой правке, но не чаще раза в 5 минут.
4. Удаление сессии уезжает в копию в течение нескольких секунд.
5. Каждые 15 минут — плановый приём; при ошибке повтор через минуту.
6. Раз в 6 часов — проверка новой версии плагина с уведомлением.

## Понятная резервная копия

В зеркале рядом с каждой сессией лежит `session.json` с названием, датой и
вложениями, а в папке проекта — `index.md` со списком всех сессий. Открыть
таблицу можно прямо на GitHub, без плагина. Подробнее — в `README.md` зеркала.

## Ограничения

- Новые сессии появляются в списке DSH после перезапуска приложения.
- Вложения дублируются только в основное хранилище.
- При синхронизации через WebDAV или API скорость ограничена каналом: первая
  выгрузка большой истории может занять часы, дальше уходят только изменения.
- Если две машины одновременно правят одну сессию, копия сохраняется как
  отдельная сессия — данные не теряются.
